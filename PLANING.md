# GLSL Support rewrite

Build **GLSL Support** as a separate, LSP-free Java plugin with a C++23 compiler library, `glsl_support.dll`. The first release will support **Windows x64** on JetBrains IDEs from **2026.1** onward. Both **Block Layout** and **Show SPIR-V** will work from 2026.1. IntelliJ IDEA **2026.3** will be the primary integration test host.

## Architecture and compatibility

- **C++ owns compilation.** Statically link glslang 16.6.0 and its matching SPIRV-Tools revisions into the DLL. Use glslang for preprocessing, typed analysis, compiler errors and warnings, cross-stage linking, and SPIR-V generation. Use SPIRV-Tools for validation and disassembly. Return compact results to Java and release compiler trees after use. [glslang release](https://github.com/KhronosGroup/glslang/releases/tag/16.6.0) · [Matching dependency revisions](https://raw.githubusercontent.com/KhronosGroup/glslang/16.6.0/known_good.json)
- **Java owns editing.** Build one error-recovering parser that preserves comments, whitespace, directives, inactive branches, and unfinished expressions. Reuse it in headless tests and IntelliJ’s Program Structure Interface (PSI). This lets formatting, completion, and navigation keep working while the user is halfway through an edit.
- **The shared plugin targets build 261 and Java 21.** Isolate newer platform integrations behind capability checks. For example, ordinary GLSL symbol search works across supported versions, while the newer Search Everywhere interface can also surface named pipelines and variants when active. [JetBrains version matrix](https://plugins.jetbrains.com/docs/intellij/build-number-ranges.html) · [Search Everywhere API changes](https://plugins.jetbrains.com/docs/intellij/api-notable-list-2026.html)
- **Use the new plugin ID `com.glslsupport.language`.** Declare the conflict with the old GLSL Analyzer so both plugins cannot claim the same files. On first load, import compatible preferences, include paths, stage macros, and variants from `glslAnalyzer.xml` and `glslVariants.xml` into the new plugin’s settings. Make the import repeatable without duplicating or overwriting subsequent edits.

## Implementation order and completion gates

Each stage must pass its checked-in tests before work advances. Organize the project into a native library, standalone Java language core, JNI bridge, IntelliJ plugin, and shared test fixtures.

| Stage | Deliverable and completion check |
|---|---|
| **1. C++23 DLL** | Start with single-shader diagnostics, then add includes and variants, pipeline linking, layout queries, and SPIR-V. Expose a versioned C interface with explicit result ownership. Run CTest against valid and invalid shaders, reference-tool output, concurrent requests, repeated compilation, and native memory checks. |
| **2. Standalone Java core** | Implement lexing and parsing first, followed by formatting, scopes, symbol resolution, completion, inspections, and refactoring edits. Run JUnit without an IDE or DLL. Convert the previous analyzer’s feature cases into reusable input-and-expected-result fixtures, including incomplete shaders and multi-file projects. |
| **3. Java/native integration** | Pass revisioned source snapshots through JNI, including unsaved headers, effective settings, and ordered macro definitions. Test UTF-8 to UTF-16 positions, nested includes, `#line`, stale results, cancellation, and missing or incompatible DLLs. Keep compilation off the UI thread and invalidate only affected shaders when a header changes. |
| **4. IntelliJ integration** | Connect the shared parser to typed PSI, stub indexes, references, and standard editor actions. Test ordinary editing, Search Everywhere, Find Usages, and Rename in IntelliJ IDEA 2026.3. Run the same core workflows on 2026.1 before adding newer integrations. |
| **5. Complete the feature set** | Deliver templates, colors, settings, documentation, and the variants UI first. Then finish project-wide refactoring, named pipelines, Block Layout, and the synchronized SPIR-V view. Track every user-facing feature from the previous plugin and analyzer against a replacement and a regression test. |
| **6. Verify features end to end** | Exercise actual IDE actions on fixture projects. Cover unopened files, unsaved headers, overloads, shadowed names, variant conflicts, preview and undo, template expansion, theme changes, layout inspection, and source-to-SPIR-V navigation. |
| **7. Verify the packaged plugin** | Install the distribution ZIP into clean IDE sandboxes. Run Plugin Verifier across advertised products and build lines 261–263. Smoke-test IntelliJ IDEA 2026.3, the installed IDEA 2026.1.2, PyCharm 2026.2.2, and CLion 2026.3. Provide one Windows command, `.\gradlew.bat checkAll`, to rerun the suites and report failures by stage. |

## Feature acceptance

- **OpenGL, Vulkan, and mixed projects.** Support desktop GLSL core and compatibility profiles, GLSL ES profiles, and Vulkan targets 1.0–1.4. Resolve settings from project to folder to file to variant. Preserve stage macros, ordered definitions, virtual `#version` overrides, active-variant live analysis, and deduplicated all-variant diagnostics on save. Named pipelines explicitly associate stage files and variants for glslang linking. Ordinary OpenGL shaders use OpenGL source-validation rules, including shaders that cannot be emitted as SPIR-V.
- **Language intelligence and editing.** Deliver type-aware completion for built-ins, extensions, overloads, fields, swizzles, and include paths. Preserve quick documentation, offline OpenGL reference pages, signature help, inlay hints, document colors, semantic highlighting, selection expansion, folding, structure view, and incoming and outgoing call hierarchies. Support whole-file, selection, and on-type formatting. Add configurable inspections for unused declarations, shadowing, and unreachable code alongside glslang diagnostics.
- **Navigation and safe refactoring.** Index unopened project files for declaration, definition, type and implementation navigation, Find Usages, and Rename. Resolve edits against the selected declaration across includes and configured variants. Deliver **Inline Local Variable** and **Extract Function** with preview and undo. Refactorings must explain ambiguous macro expansions, name collisions, or changes in evaluation order before modifying files.
- **Block Layout.** Open the view from a block, struct, or its use. Show a byte diagram and expandable member table with offsets, sizes, alignment, padding, array and matrix strides, and matrix order. Cover uniform buffers, storage buffers, and Vulkan push constants. For a standalone struct, offer a labeled `std140`, `std430`, or supported scalar-layout preview. Identify driver-dependent OpenGL layouts and show the known prefix and element stride for runtime-sized arrays. Check applicable results against emitted SPIR-V decorations. [Khronos OpenGL block layouts](https://wikis.khronos.org/opengl/GLSL_Interface_Blocks) · [Vulkan shader memory layout](https://docs.vulkan.org/guide/latest/shader_memory_layout.html)
- **Show SPIR-V.** Open a read-only disassembly beside the shader using its selected target, stage, and variant. Synchronize source lines and instructions where debug information provides a mapping, including lines from headers. Refresh after edits, identify stale output during compilation, and show actionable compiler diagnostics when generation fails. [CLion assembly view](https://www.jetbrains.com/help/clion/assembly-view-for-files.html)
- **Appearance, settings, and templates.** Give types, built-ins, functions, fields, shader interfaces, macros, and inactive code configurable colors with light, dark, and high-contrast previews. Group settings by targets and pipelines, includes and variants, and inspections. Keep formatting under IDE Code Style. Preserve existing templates and intentions, add stage templates through mesh and ray tracing, and add a `.glslh` header template with a deterministic project-relative include guard. Test that two same-named headers in different folders receive distinct guards.

The release gate will also record **warm completion latency, indexing time, single-header reanalysis cost, and peak Java and native memory** on a fixed shader corpus. Keep those benchmarks, their inputs, and the functional fixtures in the new project so future changes can be validated independently of the old repositories.
